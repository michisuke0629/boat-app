競艇データ分析アプリ 設計仕様書

24競艇場 × 6指標のマトリクス表示アプリ。Next.js 16 + Supabase + Vercel + GitHub Actions構成。

1. 全体構成

外部の2つのデータソース（BoatraceOpenAPIとboatrace.jp公式サイト）から定期的にデータを取得してSupabaseに蓄積し、 Next.jsアプリがそのデータを読み出して集計・表示する。データ取込のトリガーはGitHub Actionsの定期実行（cron）で、 Vercel上にホストされたAPI routeを呼び出す構成。

3. データソース

① BoatraceOpenAPI（出走表・直前情報・結果）

エンドポイント: https://boatraceopenapi.github.io/api/v1/{YYYY}/{YYYYMMDD}.json

対応期間 2026-01-01以降。GitHub Pagesで公開されている無料の非公式データセット。

1つのJSONに、その日開催された全競艇場・全レースの出走表(programs)・直前情報(preview)・結果(result)が スタジアム番号・レース番号をキーにした階層構造で入っている。

取得データ主なフィールド用途
出走表racers[].number（登録番号）, rank_number（級別）選手マスタの更新
直前情報preview.racers[].exhibition_time, course_numberコース別持ちタイム（要件4）、分析情報ページの展示タイム順位算出
結果result.technique_number（決まり手）, place_number（着順）, start_timing（実績ST）1着率・決まり手内訳（要件1,2）、コース別ST（要件3）、平均ST系ポイント

決まり手コード: technique_number は 1=逃げ, 2=差し, 3=まくり, 4=まくり差し, 5=抜き, 6=恵まれ。 実データ（technique_number_sourceの日本語文字列）と突合して検証済み。

② boatrace.jp 公式サイト（直接スクレイピング）

BoatraceOpenAPIには含まれない「今シリーズの得点率順位」「前検タイム」「レースタイム（周回タイム）」は、 公式サイトのHTMLページを直接取得してcheerioでパースしている（src/lib/scrape.ts）。 robots.txtで全許可（Disallow:のみ）を確認済み。

ページURL形式用途
節間得点率一覧/owpc/pc/race/pointrank?jcd={場コード}&hd={YYYYMMDD}要件5: 今シリーズ得点率順位
モーター/ボート成績・前検タイム/owpc/pc/race/rankingmotor?jcd={場コード}&hd={YYYYMMDD}要件6: 今シリーズ前検タイム（分析情報ページの前検タイム行）
レース結果/owpc/pc/race/raceresult?rno={レース番号}&jcd={場コード}&hd={YYYYMMDD}持ちタイム（今節・1枠以外の最速レースタイム）用のrace_time取込

ページ構造が変わるとスクレイピングが破綻するリスクがあるため、1件（スタジアム/レース）の取得失敗が他に波及しないよう try/catchで隔離している（src/app/api/cron/sync-series-stats/route.ts、 src/lib/ingest.tsのbackfillRaceTimes()）。 また「得点率」は初日の結果が出るまでは公式サイト側にデータが存在しない（"データがありません"ページが返る）ため、 その場合は0件のまま次回実行を待つ。

レース結果ページの規模とmaxDuration対策: 得点率・前検タイムは「スタジアム×日」で1リクエストだが、レースタイムは レースごとに1リクエストが必要（1スタジアム最大12R）。開催中の全スタジアムを毎日取り切ると 1日あたり最大250〜300リクエスト程度になり、VercelのmaxDuration=60秒に収まらずタイムアウトする （2026-08-17・08-18にsync-day-yesterdayジョブがexit code 22で失敗した実際の原因）。 そのためsync-dayからレースタイム取込を切り離し、専用のbackfillRaceTimes()が 「着順確定済みだがrace_time未取得」のレースを日付降順（直近優先）で30件だけ拾って処理する形にした。 同時実行数6のワーカープールで処理し、失敗・未処理のレースは次回以降のsync-race-timescronで再取得される。

4. データベース設計

スキーマ定義: supabase/schema.sql

racers選手マスタ
racer_number (PK), name, rank_number, branch_number
seriesシリーズ（節）
id (PK), stadium_number, start_date, end_date, title
racesレース（決まり手はここ）
date+stadium_number+race_number (PK), technique_number, series_id (FK)
race_entries出走エントリー
+entry_number (PK), racer_number, course_number, start_timing, start_rank, place_number, exhibition_time, exhibition_rank, race_time
series_point_ranks得点率（要件5）
series_id+racer_number (PK), rank_position, point_rate, points, deduction
series_precheck前検タイム（要件6）
series_id+racer_number (PK), rank_position, precheck_time, motor/boat番号・2連対率

race_entriesの追加カラム（分析情報ページのポイント系指標用）: start_rank・exhibition_rankは、同一レース内の6艇のスタートタイミング／展示タイムを比較した 「レース内順位」（1が最速）で、ingestDay()がBoatraceOpenAPIのレースデータだけから算出する （追加のスクレイピング不要）。race_timeはboatrace.jpのレース結果ページからのスクレイピングでのみ 埋まるため、いずれもこの列を追加した日以降に取り込まれたレースからしか値が入らない（過去分は全件バックフィルしていない）。

シリーズ（節）の自動検出: BoatraceOpenAPIの day_number（開催何日目か）が1に戻ったスタジアムを 「新シリーズ開始」とみなし、直前の進行中シリーズにend_dateを確定してから新しいseries行を作成する （src/lib/ingest.tsのingestDay()）。各races行には、その時点で 「進行中」と判定されたシリーズのIDをseries_idとして直接持たせているため、集計時に日付レンジ結合ではなく 単純なFK参照で「直近N場」を絞り込める。

過去の不具合と対処（記録として）: 当初 rank という列名を使っていたが、PostgreSQLの組み込み順序集合集約関数 rank() と衝突し、SELECT時に WITHIN GROUP is required for ordered-set aggregate rank エラーが発生した。rank_positionにリネームして解決している。

5. データ取込の実装

共通ロジック

ファイル役割
src/lib/kyotei-api.tsBoatraceOpenAPIの日次JSON取得・型定義
src/lib/scrape.tsboatrace.jpの得点率・前検タイム・レース結果（レースタイム）ページのスクレイピング
src/lib/ingest.tsingestDay(): 1日分のデータをracers/races/race_entries/seriesへupsertする共通処理（cron routeとbackfillスクリプトで共用）。 同時にレース内のstart_rank/exhibition_rankも算出する。
backfillRaceTimes(limit): 着順確定済みだが race_time未取得のレースを日付降順でlimit件だけ拾い、レース結果ページをスクレイピングして補完 （同時実行数6のワーカープール、失敗は次回cronで再取得）
src/lib/aggregate.ts6指標＋本日のレース分析情報の集計ロジック（Server Componentから呼び出し）

API routes（Vercel上で動作、GitHub ActionsからBearerトークンで認証）

Route処理内容
POST /api/cron/sync-day指定日（省略時は当日JST）のBoatraceOpenAPIデータを取込（ingestDay()）。 ?date=YYYY-MM-DDで任意日を指定可能。maxDuration=60
POST /api/cron/sync-series-stats現在進行中の全シリーズ（end_date is null）について、得点率・前検タイムをスクレイピングして更新
POST /api/cron/sync-race-times着順確定済みだがrace_time未取得のレースを日付降順で30件だけ処理（backfillRaceTimes(30)）。 20分おきに実行し、複数回に分けてレースタイムの取りこぼしを解消する。maxDuration=60

認証は Authorization: Bearer <CRON_SECRET> ヘッダーで行い、環境変数 CRON_SECRET と一致しない場合は401を返す。

初回バックフィル

scripts/backfill.ts（npm run backfill）を手動で一度だけ実行し、 BoatraceOpenAPI対応開始日（2026-01-01）から前日までの日次データを一括投入する。1日ずつingestDay()を 呼び出し、150msのウェイトを挟んで対象サイトへの負荷を抑えている。得点率・前検タイムはスクレイピングのため 過去分は取得できず、稼働開始後に開催されたシリーズから蓄積される。

データ量がスタジアム単位で高々数千行程度のため、DB側でGROUP BYするSQL/RPCは作らず、 必要な行をSupabaseから取得してJS側（Node/Next.jsサーバー）で集計する設計にしている。

7. 本日のレース・分析情報

トップページ（/）は当初の6指標マトリクスから、レイアウトExcel（assets/レイアウト.xlsx） 準拠の「本日のレース」画面へ全面刷新している。各レースの分析情報ページ（getRaceCardAnalysis()）が中心の機能で、 出走6艇を横に並べたスプレッドシート風の表（src/components/AnalysisTable.tsx）で表示する。

項目データソース・算出方法
持ちタイム今節（進行中シリーズ）・進入コース≠1の中でrace_timeが最小のレースを採用
前検タイムseries_precheck.precheck_time（今シリーズの前検、要件6と同じ値）
枠別着率／コース別決まり手率／決まり手数そのレーサーの全国横断の過去出走履歴（race_entriesをracer_numberで横断検索）を、 今日のこのレースでの進入コースで絞り込んで集計
平均ST ポイント／平均ST順位 ポイント進入コースでの平均ST・平均STレース内順位を、前期・直近6/3/1ヶ月の4期間で出走6艇比較
全枠順平均ST ポイント全コースでの平均STを、前期・直近3/1ヶ月の3期間（直近6ヶ月は含めない）で比較
全枠順平均ST順位 ポイント全コースでの平均STレース内順位を、直近3/1ヶ月の2期間のみで比較
展示タイム勝率ポイント直近1年で展示タイムが出走6艇中1位だったレースに絞り、1位回数・1着率・2連対率・3連対率の4項目で比較

ポイント系5項目はいずれも同じ採点ルール（scoreTop2()）を使う：値を小数点2桁に丸めて出走6艇を比較し、 最良1位に2pt・2位に1ptを付与（1位が同値の場合は両方1位扱いで2位は不在）、対象期間・項目数ぶん合計する。 分析情報ページには算出根拠を確認できる「＜ポイント詳細＞」表も併設し、scoreTop2()の判定結果を再利用して 1位セルを赤・2位セルを黄でハイライトする。

「前期」の定義: ボートレースの選手級別レーティング期間（11/1〜翌4/30が前期、5/1〜10/31が後期）に合わせ、 getPreviousZenkiRange()が現在日時点で直近に完了している前期の期間を動的に算出する （進行中の期間は含めない）。前期の全期間を取得できるよう、レーサー履歴取得の開始日は「前期開始日」と「直近1年」の早い方に合わせている。

10. 既知の制約

  • BoatraceOpenAPIは2026-01-01以降のデータしか提供していないため、サービス開始直後は「直近10場」等の指標が 指定場数に届かない競艇場がある（画面上に注記表示）。
  • 得点率・前検タイムはスクレイピングのため過去分は遡れず、稼働開始後に開催されたシリーズから蓄積される。
  • race_time・start_rank・exhibition_rankは列追加後に取り込まれたレースからしか 値が入らない。導入時は進行中シリーズ分のみ手動で再取込（バックフィル）しており、それより古いレースは 平均ST系ポイント・持ちタイムの算出対象から自然に外れる（値がnullのため）。
  • boatrace.jpのページ構造が変わるとスクレイピングが失敗する可能性がある（1件単位でtry/catchしているため 他への影響は限定的）。レース結果ページはレースごとに1リクエストが必要なため、得点率・前検タイムよりスクレイピング 量が多く、サイト負荷やブロックのリスクも相対的に高い。
  • GitHub Actionsのscheduleは指定時刻ちょうどに実行される保証がなく、数分〜十数分程度前後する。
